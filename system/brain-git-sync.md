# Brain git sync — how a brand brain talks to GitHub, and how we make agents do it right

The runtime procedure lives in the routine bundle as the `save-brain` skill (`templates/brand-routines/claude/skills/save-brain/SKILL.md`, shipped to brains at `.claude/skills/save-brain/`). This doc is the maintainer's side: the facts the procedure rests on, the enforcement stack that makes agents actually follow it, and why each piece exists. Change the procedure there, check the reasoning here.

## The facts underneath (from the Parker MCP server)

- Managed brains live in the **`parker-brain` GitHub org** (server env `GITHUB_PARKER_ORG`), one private repo per brand, named `<org>-<brand>` or `<brand>`, provisioned by `setup_parker_brain`.
- Git auth is the **machine-level Parker sync helper** (`@heyparker/sync`, installed once per machine by `npx @heyparker/sync setup`): a git credential helper at `~/.parker/bin/parker-credential`, wired into the user's global git config scoped to `https://github.com/parker-brain/` only. On every git network operation, git invokes the helper, the helper calls the Parker backend (mevin2's `/api/git-credential`), and the backend checks the user's brand membership and mints a **GitHub App installation token** — ≤1 hour, scoped to that single repo, `contents: write` only — returned straight to git over the credential protocol. No token is ever stored, printed, or handled by the agent; expiry is invisible because every operation mints fresh. `setup_parker_brain` still provisions the repo, but it is out of the auth path entirely.
- Human collaborators are added at write permission via the same tool (`github_username` param, invitation flow). Their personal auth is for *their* clones on *their* machines — never for the agent.
- Repos have **no branch protection** and the default branch is whatever the first push created (`main`). This is why the procedure bans force-pushes and branches outright rather than relying on GitHub to stop them.

## Why the agent must never use the user's auth or `gh` on the managed repo

The user usually has no working GitHub auth in the session at all (they were invited, or never touched GitHub). When they *do*, using it against the managed repo misattributes commits, sidesteps the access Parker manages, and — for `gh` specifically — habituates a tool that will be missing or wrongly-logged-in in most brand sessions. One credential path means one failure mode and one fix: re-call the tool. The scope is the managed repo, not the tool: `gh` pointed at *other* repos (searching GitHub, reading another project) is the user's own business and passes the guard.

## Credentials live behind a machine-level helper (and how we got here)

`origin` carries the **plain** URL (`https://github.com/parker-brain/<repo>.git`), and no credential exists anywhere in the repo, the agent's context, or a shell command. The one-time `npx @heyparker/sync setup` signs the user into Parker (browser device flow — no GitHub account needed), installs `~/.parker/bin/parker-credential`, and writes a global gitconfig block scoped to the managed org:

```
[credential "https://github.com/parker-brain/"]
    helper =
    helper = ~/.parker/bin/parker-credential
    useHttpPath = true
```

The blank first entry is still load-bearing: helper lists accumulate across config scopes, and macOS git ships a system-level `osxkeychain` helper that would otherwise answer *first* with the user's personal GitHub credential — pushing to the managed repo as them, the exact misattribution this design bans. The empty entry clears the inherited list *within the org scope only*, so the user's own GitHub auth elsewhere is untouched. `useHttpPath` makes git pass the full repo path to the helper, so one helper serves every brand and the backend can downscope each mint to exactly the repo being touched. Plain `git clone --recurse-submodules`, `git pull --rebase origin main`, and `git push origin main` just work, on every managed repo, wherever it sits on disk. Explicit `origin main` on every push so nothing depends on upstream config that a fresh clone doesn't have.

This is the fourth revision, and each move was forced. v5 bracketed every sync with token-in/token-out `set-url` calls so no secret lingered in `.git/config`; the ceremony was worse than the risk — agents skipped pushes or stalled asking the user — so v6 left the tokenized URL sitting in `origin`. v6 died on **Claude Code's permission classifier refusing any Bash command that carries a live token** ("Credential Leakage"), which killed the refresh (`set-url` with a tokenized URL) and the tokenized clone. v8 moved the token into git's store file `.git/parker-credentials`, written with the Write tool so it never transited a shell command, with per-repo two-entry helper wiring; v10 pre-approved those writes in the bundle's settings. In practice the classifier still blocked the token Write **most of the time** — pre-approval rules helped only on unedited settings, the agent was still the token's courier (tool result → context → file), every hour meant another mint-and-write dance, and the per-repo wiring later *shadowed* any better auth and broke pulls with username/password prompts. v15 removes the agent from the loop entirely: the **@heyparker/sync credential helper** is git's own intended extension point, the token is minted server-side per operation and returned directly to git, nothing persists client-side, and there is nothing left for a classifier to object to — the agent's whole git vocabulary is plain `clone`/`pull`/`push`. Revocation also improves: membership removed in Parker means the next mint is refused, within the hour, per repo — versus rotating nothing-revocable file copies.

The transition duty the procedure carries: every pre-v15 brain has the retired per-repo wiring on disk, and it must be **cleaned, not obeyed** — `git config --local --unset-all credential.helper`, delete `.git/parker-credentials`, strip a pre-v8 tokenized origin. The session-start hook performs this cleanup deterministically when a pull fails auth (no command in it carries a secret), the skill teaches it, and `migrations/v15.md` walks standing brains through it once.

## Detecting the self-hosted exception

A rare team hosts the brain in their own GitHub instead of the managed org. Detection is the origin URL: `github.com/parker-brain/…` → managed, anything else → theirs, their auth, `gh` allowed. A repo with no remote yet counts as managed when `parker_config.json` exists (mid-build). Both the skill and the guard hook use exactly this test, so the exception needs no configuration.

## The enforcement stack (instructions alone don't survive contact)

1. **`git-guard.py`** — PreToolUse hook on Bash in the shipped `.claude/settings.json`. Deterministic: on managed repos it blocks `gh` aimed at this repo (naming the managed org, or a repo-context subcommand — pr, issue, release, run, and kin — with no `-R`/`--repo` pointing elsewhere; `gh` against other targets passes), any command carrying a raw token (`x-access-token:` in the command — hand-carried tokens are the retired flow; the guard teaches the helper at the moment of the mistake), `push`/`pull`/`fetch` on a machine with no auth path (satisfied by the machine-level helper — `~/.parker/bin/parker-credential` or the org-scoped global gitconfig — or, mid-transition, by a legacy non-empty `.git/parker-credentials` or token-in-origin), any force-push, and clones missing `--recurse-submodules` (a plain clone is otherwise the standard; it blocks a clone only on a helper-less machine). Ops on the public mount (`git -C parker-system …`) pass through. It fails open internally, and its settings entry must never get the `2>/dev/null || true` wrapper the other hooks use — exit code 2 and stderr are the mechanism.
2. **`session-start.py`** — the pull-first enforcement. On session start it *runs* `git pull --rebase origin main` + submodule update itself when the working tree is clean, instead of only reminding; on an auth failure it first performs the deterministic legacy cleanup (unset the retired repo-local `credential.helper`, delete the retired store file, strip a tokenized origin — no secrets in any of it) and retries once, and only then reports loudly — naming the missing-helper fix (`npx @heyparker/sync setup`, user present) when that's the cause — making the pull the session's first job. It deliberately does **not** synchronize factory tags: tags do not affect the checked-out submodule pin, and release discovery belongs only to `/update-brain`, which runs `git -C parker-system fetch origin --prune --prune-tags` before comparing releases.
3. **The `save-brain` skill** — the full procedure, discoverable by name and description for anything save/sync/clone-shaped, and the reference the guard's messages point to. Self-contained on purpose: git trouble often happens exactly when the mount is empty.
4. **The brand `CLAUDE.md` section** ("How this brain saves itself") — always loaded, carries the two absolutes: pull first, and commit-and-push immediately without ever asking the user for permission to save. The push-always discipline is deliberately prompt-level, not a hook: a Stop-hook version was built and removed, because a blocking guard risks trapping a turn behind a persistent git error and can't see an explicit "don't commit" from the user — the two absolutes plus the end-of-turn self-check (and the user-override carve-out) live here and in the skill instead.
5. **The tool's own returned message** (mevin2 side) — the one channel that reaches sessions outside the repo, e.g. claude.ai during onboarding. It should now teach: repo provisioned, auth is machine-level — run `npx @heyparker/sync setup` once if the helper is missing, then plain `git clone --recurse-submodules <plain URL>`. Once standing brains have migrated, the tool should stop returning `credential_file_line` / `authenticated_clone_url` at all — a token in a tool result sits in model context and transcripts for no remaining reason. Keeping it consistent with the skill is a cross-repo duty, and until it catches up, the skill and hooks here override what the tool message says.

Layers 1–4 travel in the routine bundle, so `sync-executable-layer.py` delivers them to standing brains on a pin bump; only a team-customized `settings.json` needs the migration's manual merge.
