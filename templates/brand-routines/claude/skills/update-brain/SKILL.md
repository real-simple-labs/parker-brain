# Update brain — keep the method current, never touch the team's work

The factory keeps improving after a brain ships: new method docs, sharper skills, new prompts, new system machinery. And a brain's own build can have holes — a source pull that never ran, a doc a dead session skipped. Left alone, both kinds of gap are invisible: the freshness system re-runs what is stale but cannot see what is missing, and a brain never learns the factory grew. This routine is the eyes for both — it finds every gap between this brain and the current standard, installs the safe part of it, and turns the rest into an offer.

**The one rule that governs everything here: update the method, never override the team.** This brain belongs to the team. A doc they deleted was deleted for a reason. A skill they modified is theirs now. A gap they declined to fill last month is a decision, not an oversight. What arrives on its own is only what was never theirs: the pinned factory release, the copies of factory files they never touched, and migrations the factory marked safe to run with nobody there. Those can make mechanical changes to the brain's own files (a new file copied in, a sentence added to or swapped in `CLAUDE.md`, a line in the ledger), and every one is reported afterwards. Everything else the team wrote or changed stays exactly as they left it, and anything that needs their judgment waits for their yes. Most releases are safe, so asking about every one only kept brains behind (team decision, 2026-10-09, v40); the team can still turn automatic updates off at any time and get one question per release instead.

## When it runs

**Weekly** as a scheduled routine, early Monday, so the week starts on the current release. Also runnable on demand whenever someone asks what's new or wants to bring the brain up to the standard.

## Terminology

Remember that most users are likely unfamiliar with git, so don't confuse the user with terms like "diff", "push to main", "pull a tag" - use commonly understood terms like "changes", "save new files", "download a new version". When describing changes, do it from a non-technical perspective: "improved the monthly report" instead of "refactored the report validation script". 

## The two comparisons

### 1. The brain vs the current factory — what's new in the standard

Read the brain's update posture from `running-notes/standard-sync.md` first — it decides which of two shapes this comparison takes. If the ledger is missing or unreadable, say so plainly and stop; never guess at what the standard contains.

Before deciding the mode or doing any comparison, also read `parker-system/migrations/README.md` and any `migrations/vN.md` newer than this brain's last-applied migration — a release can change the filesystem shape or how the two modes work, and that context belongs in the comparison before the offer is framed.

**Finish what an earlier update left.** If the ledger's **Migrations applied through** is older than its **Pinned release** (the release `parker-system/` is checked out at), an earlier update stopped partway: a migration had a step that couldn't run yet, so it did not record its release. Only finish it from a copy that saves (the same rule as "Only from a copy that saves" below): anywhere else, say so plainly and leave the walk, its pending offers included, for a run that saves. Before any comparison, apply each missing `migrations/vN.md` in order, as written (they are safe to run again, and their finished steps skip themselves), under the same record rule as the bump below: a migration has finished only when its own last line says to record it, and only then does **Migrations applied through** move to its release (`update-brain.py record-migration <vN>`). With nobody there, run only the ones `plan` marks `auto_apply`; the first that isn't ends the walk and waits for a person. If one stops again, or a step of it is answered "not now", end this walk there, say why in plain words, leave the field where it is, and go on with the rest of the routine. Nothing newer installs on its own until this walk is done: `plan` keeps `auto_target` empty while a migration is unfinished.

**Connected mode — `parker-system/` is a pinned submodule and the posture is `follow` (the standard shape).** The factory arrives whole or not at all, so there is no per-file diffing of the method: the update is the *release*. Before comparing, synchronize the factory's tag refs with `git -C parker-system fetch origin --prune --prune-tags`. This replaces a moved tag and removes a tag deleted from the factory, so an old local ref can never be mistaken for a release. (Mount operations like this are the one kind of git the brain still runs itself — local, credential-free, against the public factory; the brand repo's own syncing is Parker Desktop's job, per `/save-brain`.) Then run `python3 parker-system/scripts/update-brain.py plan` from the brain's root folder. It reads the ledger, the mount, and the tags, and prints one JSON object; it is the truth about what this brain may take on its own, so never work that out by hand. If the script is missing or fails, nothing installs on its own this run: offer the newest release as the one question, as before v40, and say why in the digest.

What it returns:

- `unfinished_migrations` and `resume_sync_from` — what an earlier update left. Handle them first, as "Finish what an earlier update left" says: run the ones marked `auto_apply` (they are safe to run unattended), and leave one that isn't for a person. When `resume_sync_from` is set, the pin moved but the update stopped before recording it: after the migrations, run `sync-executable-layer.py --from <resume_sync_from>` and then `update-brain.py record-pin <mount_at>`. Then run `plan` again.
- `auto_target` — the newest release this brain may take with nobody asked: every migration on the way is safe to run unattended, automatic updates are on, no build is underway, and nothing earlier is unfinished. `null` means none, and `why_not_auto` says why in plain words.
- `offer_target` and `stopped_at` — the newest release, and the first migration on the way that needs a person (`stopped_at`). What `auto_target` doesn't reach is offered as one short question.

If the pin is current, this comparison is one line in the digest. If the factory has moved:

- Name the new release and what changed — the factory's `release-notes/` entries and `migrations/` files between the pinned tag and the new one say exactly this; read them and put it in plain words.
- **Only from a copy that saves.** That is the copy Parker Desktop uploads, or, in a scheduled cloud run, the copy `cloud-run-git.py clone` made, which the run saves with `cloud-run-git.py save` (per `/save-brain`'s "In a cloud run"), or a self-managed brain's own folder (the ledger says the repo is self-managed), which the team commits themselves. If this session is in none of these, or the app shows the brain as read-only for this person, don't take the update here: nothing would be saved, and the app would put the old pin back. Say so plainly, and leave the update for someone who can edit the brain. Don't write the offer to the ledger here either: nothing written in this copy reaches the team, and the next run in a copy that saves makes the same offer.
- **Up to `auto_target`, take it without asking.** Follow "Taking a release" below, then tell the team what happened in the closing summary. Nothing is put to them first.
- **Past `auto_target`** (up to `offer_target`), **or when `auto_target` is `null`**, offer the bump as the one question from "Keep it quick". On a yes, follow "Taking a release" for the offered release. A migration that needs a person runs with them there, as it always has: it shows the team what it would change in their own content before it changes it.

**Taking a release.** Before anything moves, run `python3 parker-system/scripts/sync-executable-layer.py --from <pinned release> --to <release> --dry-run`. If it fails, stop: nothing has changed, say so plainly, and leave the offer in the ledger. Then check out the release in `parker-system/` (`git -C parker-system checkout <tag>`, run from the brain's root folder — a local mount operation). Don't stage or commit the moved pin: Parker Desktop's next sync commits it with everything else before it re-aligns the mount, a cloud run's `save` commits it with the rest, and a self-managed team commits it themselves. Then walk the factory's `migrations/` files in order — every `vN.md` after the ledger's **Migrations applied through**, up to the new pin (normally that is the old pin; it is older when an earlier migration stopped partway) — and apply each as written (they are agent-executable instructions: layout moves, re-runs, new files outside the copied bundle). A migration marked `**Auto-apply:** yes` makes its edits to the brain's own files without showing them first, since they're mechanical and checked; keep a note of each file it changed and what it added or swapped, for the closing summary. Any other migration that touches the brain's own data is still shown before applying. With nobody there, an offer step inside a marked migration (re-arm a routine, try something new) goes into the ledger's offer history as pending and finishes the step; the next session with someone there asks it. **Record each migration when it finishes, and only then:** a migration has finished when its own last line says to record it; run `python3 parker-system/scripts/update-brain.py record-migration <vN>` at that point (it refuses to skip one), and only then go on to the next. If one stops partway, or a step of it was answered "not now" (it says which), end the walk there and leave the field where it is: later migrations may build on it, and the next run finishes them in order before it takes anything newer. A migration that already stopped earlier in this run (under "Finish what an earlier update left") ends this walk at once: don't run it again in the same run, where it would only stop again or ask its question twice. Then re-sync the **copied executable layer** — the craft skills, routine skills, review-gate agents, hooks, checker scripts, and the Codex twin (`.codex/`, root `AGENTS.md`) the build copied out of the mount into `.claude/`, `.codex/`, `scripts/`, and `schedules/` — by running `python3 parker-system/scripts/sync-executable-layer.py --from <old pin>`. The script applies the three piles below deterministically: untouched copies refresh silently, team-edited files stay theirs and are listed, nothing is deleted. Its report is the truth — never re-diff those files by hand, and never turn its per-file lines into questions. If it fails, run it once more (it is safe to repeat); if it fails again, stop without recording the pin and say so plainly: the next run's `plan` sees the moved pin as `resume_sync_from` and finishes it. Finally record the new release with `python3 parker-system/scripts/update-brain.py record-pin <tag>`, which sets **Pinned release** in the ledger and `parker_brain_version` in `parker_config.json`, and only when the mount really is at that tag; **Migrations applied through** only ever moves migration by migration, as above. Add a line to the ledger's offer history ("taken automatically" or "taken"), and the moved pin and every synced file save like any other change. One Codex-specific note for the digest: if the sync added or refreshed `.codex/config.toml`, teammates who use Codex will be re-asked to approve the hooks on their next session there (a changed hook definition needs approval; updating its delegated script alone does not). Verify the effective `parker-brain` permission profile after v17: legacy sandbox settings can override it. If a scoped pin update or copied-config write requires approval, request that specific operation rather than disabling the daily protection.
- Never edit anything *inside* `parker-system/` — the mount is read-only; an update is only ever the pin moving.

**Decoupled mode — the posture is `own-factory` or `independent`, and `parker-system/` is the team's own vendored copy (or their own factory fork).** The team owns their method now, so the comparison is informational: fetch the public factory (shallow clone; the remote is recorded in the ledger), compare the methodology layers — the generating prompts, the craft knowledge in `parker-system/creative-strategy-context/`, the runtime system docs, the skills — and sort every difference into three honest piles:

- **New in the factory, absent here** — a method doc, skill, prompt, or system doc the factory added since this brain decoupled. These are the main offers: name each, say in one plain line what it does and why the factory added it, and offer to bring it in.
- **Changed in the factory, unmodified here** — the brain's copy matches an older factory version. Offer the refresh; this is the safe pile, since the team never touched theirs.
- **Changed here, by the team** — the brain's copy differs from every factory version because the team edited it. **Theirs wins, full stop.** Surface it once as a note ("your scriptwriting skill has local changes; the factory version also moved — want to see what changed there?") and never offer it again unless the factory ships something newer still.

Under `independent`, soften even that: one "FYI, the factory moved" line in the digest unless they've asked for offers. Automatic updates never apply to a decoupled brain, under either posture: the team owns its method, so every change stays an offer, whatever the ledger's **Auto-update** line says.

In both modes, the brand lens, `expert-insights/`, and everything outside the methodology layers are never even compared — they are brand property, invisible to this routine.

### 2. The brain vs its own canonical build — what was never generated

Walk the generating prompts the brain ships in `parker-system/prompts/` against the standing docs actually on disk, using the build's own path map (shipped inert in `parker-system/prompts/onboarding-runner.md`). Every prompt whose standing output does not exist at its flat path is a hole the freshness system cannot see — a persona source pull that never ran, a sub-context slice a dead session skipped, a VoC category that came back empty and was never retried. This walk is an existence check only — does the doc exist at its path — never a read of doc contents, and it never becomes questions: its whole result is one line in the digest ("2 standing docs were never generated: X, Y — ask me to fill them"). Generate a missing doc only when the user explicitly asks, running its prompt in full through the brain's own methodology, exactly as a build would have. A doc the team deliberately deleted lands here too — which is why the ledger's memory applies: a hole they declined to fill stays out of the digest until something changes. **Skip this walk while the brain isn't built yet**: a `.scaffolded` file at the root, or a `BUILD-STATUS.md` at the root that isn't marked complete (the marker comes off once a build finishes its first phase, so mid-build it's usually gone). Every standing doc the build hasn't reached is missing by design. Its digest line is instead "This brain hasn't been built yet; `/set-up-brain` builds it," or, with a `BUILD-STATUS.md` at the root not marked complete, "The build hasn't finished; `/set-up-brain` resumes it." A `BUILD-STATUS.md` at the root that is marked complete means the build finished and only its closeout didn't run, with or without the marker: the digest line is "The build finished but its last cleanup step didn't run; `/set-up-brain` finishes it," and without the marker the walk runs as usual.

## Keep it quick

On the standard layout a routine update is a two-minute job, not a review session. An automatic update asks nothing at all. When a release is offered instead, that is one question per update, total: "New Parker update: vA → vB — <one plain sentence from the release notes>. <why it waits: one plain line, from `stopped_at` or `why_not_auto`>. Recommended — want it?" with short options (Take it / Skip / What changed?). Before the yes, do nothing beyond reading the release notes and migration files for the range — no diffing, no file-by-file analysis, no inventory of the brain. Never enumerate synced or skipped files inside a question, and keep option labels to a few words; "What changed?" is where the detail lives for whoever wants it. A team-edited file the sync script leaves alone is a one-line note in the closing summary, never a question. Close with a summary of five lines or fewer: the release taken (and that it installed on its own, when it did), what the script refreshed (counts, not file lists), any of the brain's own files a migration changed and what it added in plain words ("added one sentence about updates to CLAUDE.md"), what stayed theirs, anything still offered, and any holes. After an automatic update, end with one plain line on how to switch it off: "Want to OK each update yourself instead? Say so and I'll turn automatic updates off."

## The memory — decline once, not weekly

`running-notes/standard-sync.md` is this routine's ledger: the factory remote, the update posture (`follow` / `own-factory` / `independent`), whether automatic updates are on (**Auto-update:** `on` / `off`; a ledger without the line counts as on, since taking v40 was the team's yes to it), the release the brain is pinned to (or was last compared against), which migrations have been applied, and every offer with its answer — taken automatically, taken (and when), declined (and why, when they gave a reason), or deferred. A declined offer is not raised again unless the factory version of that item has changed since the decline. This is what makes the routine a colleague and not a nag: it remembers what the team already said.

**Turning automatic updates off or on.** When someone asks to approve each update themselves (or to stop automatic updates), run `python3 parker-system/scripts/update-brain.py auto-update off`, add a line to the offer history with the date and their reason, and say plainly that from now on each release comes as one question. `auto-update on` turns it back on. Never flip it on the team's behalf.

One connected-mode caveat on that memory: if the team declined an earlier release and later accepts a newer one, every migration between the old pin and the new one still runs. Declining a *release offer* does not skip the migrations those releases carried — the pin bump walks `vN.md` in order for the whole range. A declined release that waits on a migration needing a person stays quiet until a newer release arrives; an automatic update never takes it past that migration, because `auto_target` stops before it.

## How the updates land

- **In an interactive run**, ask any offers a migration left pending in the ledger first, take what `auto_target` reaches without asking, then offer anything past it through the popup question form and apply what they take on the spot. On the standard layout that means at most the one release question from "Keep it quick" — the sync script handles the files, no per-file choices. Only a decoupled brain gets the grouped offer list (new craft, changed docs, missing outputs), each with take / decline / show-me-more choices. Whatever they take: stamp everything with its source and date, and update `refresh-schedule.md` and any affected INDEX in the same pass.
- **In a scheduled run with nobody there**, take what `auto_target` reaches, exactly as an interactive run would, and save it the cloud-run way (`cloud-run-git.py save`). Apply nothing past it: a migration that needs a person never runs without one, and a decoupled brain gets offers only. Write what's left to the ledger and the digest (after synchronizing the factory tag refs, `sync-executable-layer.py --from <pinned release> --to <newest tag> --dry-run` is how a scheduled run sees what the rest would touch — no checkout, nothing moves), and let the next conversation (or the user's tap) carry the decisions. If the routine's own prompt says to apply nothing (it was armed before v40), the prompt wins for that run: write the offer as before, and say in the digest that re-arming it with `/setup-routines` lets scheduled runs install safe releases. The Monday morning message reads "Parker updated itself to vB: <one plain line>," then names any of the brain's own files a migration changed and what it added in plain words (or "nothing of yours changed" when none did), plus anything still waiting on them.
- **Either way, the digest is plain:** what installed and why it matters, what's still offered and why it waits, what's missing and what it would add, what was declined before and stayed declined. In Parker's voice, sized to what's actually there — a week with nothing new is one line, not a report.

## Hard rules

- **Automatic only where it's safe, and only the method.** With nobody asked, this routine moves the pin up to `auto_target`, runs the migrations the factory marked safe to run unattended, and lets the sync script refresh untouched copies. Nothing else happens without the user's explicit yes: not a migration that needs a person, not a regenerated doc, not an edit to the team's files beyond what a marked migration names, and never anything in a decoupled brain or with automatic updates turned off. Every edit to the team's own files is reported in the closing summary.
- **The team's changes always win.** A locally modified file is surfaced once and left alone. Deleted is a decision. The brand lens and expert-insights are never compared, never offered against.
- **The mount is untouchable.** In connected mode, never write inside `parker-system/` — an update is the pin moving to a new release tag plus the migrations that release ships, nothing else. A brain that wants to edit the method decouples first (`/disconnect-factory`).
- **Remember the answers.** The ledger is read before any offer is made; a declined item stays quiet until the factory moves again, and an **Auto-update:** `off` stays off until the team turns it back on.
- **Never skip a migration, never record what didn't happen.** `update-brain.py` records a migration only right after the last one recorded and a pin only when the mount is on it. If it refuses, something went wrong: stop and say so, never edit the ledger by hand to get past it.
- **Generate, don't fabricate.** A missing standing doc is filled by running its own generating prompt in full — never by writing a summary that looks like one.
- **Methodology comes from the factory; brand truth comes from the brand.** This routine copies method and generates outputs from data. It never invents brand content to fill a hole.
- Ask through the popup question form whenever a run needs the user; a question in plain chat strands the routine.
- Honor the brand hard rules on anything regenerated.

## Deliverable

A brain that stays on the current standard without anyone having to ask, and whose owner always knows exactly how it differs from it — every safe release installed and reported in one plain line, every gap that needs them offered with a plain reason, every taken item applied cleanly with provenance and fresh stamps, every declined item remembered — and a `running-notes/standard-sync.md` ledger that carries the whole history of what installed, what was offered, and what the team chose.
