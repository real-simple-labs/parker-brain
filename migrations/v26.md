# v26 — cloud routines carry their key command

**Applies to:** brains on the standard layout (pinned `parker-system/` submodule, origin under `parker-brain/`). Self-managed brains (any other origin) sync their own way: skip the step.

**What changes:** the routines v24 armed still could not save. A Claude cloud routine runs in auto mode, and its safety check stopped the run's first step, the one-hour key for Parker's git server, as "Unauthorized Persistence": the command came from the Parker tool's text, which the check never sees, so the key looked like the agent's own idea. The same command in the routine's own prompt passes (tested on 2026-09-30: key, clone, commit and push to `main`). From v26 the prompt `/setup-routines` writes carries that command, and the key lives only in git's memory, never in a file. The re-sync delivers `setup-routines`, `save-brain` ("In a cloud run") and `session-start.py`. Routines armed with the v24 prompt have to be armed again. The maintainer contract is `parker-system/system/brain-sync.md`.

## Step 1 — re-arm cloud routines

Migrations run before the re-sync, so while this runs during an update the brain's own `.claude/skills/setup-routines/` can still be the old copy. Follow the new one from the mount, `parker-system/templates/brand-routines/claude/skills/setup-routines/SKILL.md`; its paths are the brain's (`schedules/` at the brain's root).

1. List this account's live schedules via `/schedule`, and read the status lines in `schedules/*.md`: they are the only view of routines armed from a teammate's account. If neither shows an active routine for this brand (live names carry its prefix, "[brand]: dream", …), skip the rest. A routine whose status line already says "saves in a cloud run (v26)" is done.
2. Only when a routine is left to re-arm, check the Parker MCP. If it has no `register_parker_brain_git_credential` tool, **stop this migration here**: tell the team that re-arming waits for that tool, and do **not** record `v26`. The next `/update-brain` run finishes this migration first.
3. For this account's other routines, offer to re-arm them with that `setup-routines`, and record the answer in the ledger like any other offer. A **"not now"** is a stop too: stop this migration here, say it will come back, and don't record `v26`. Only a yes (and the re-arm done) or a no finishes this step. The re-arm updates each routine in place: the cloud-run preamble with the key command in its prompt, the Parker MCP attached, a source repository that isn't the brain's, and a cloud environment that can reach `git.heyparker.ai` (full network access, or that host allowed).
4. A routine whose status line says another person armed it, and doesn't say "saves in a cloud run (v26)", can be re-armed only from that person's account. Add "needs re-arm (v26): run `/setup-routines` from the account that armed it" to each such line that doesn't have it yet (it replaces a "needs re-arm (v24)" note), and tell the team who needs to do it. The note goes when that person runs `/setup-routines` (it rewrites the line) or when the team says the routine is gone (mark it retired). While any status line still has the note, stop this migration here and don't record `v26`: the next `/update-brain` run checks again.
5. Routines the team made themselves (outside `/setup-routines`) aren't touched. If they asked for them, tell them that such a routine saves only when its prompt starts with the preamble in `setup-routines` step 2, key command included.

Record `v26` in `running-notes/standard-sync.md` once no active routine for this brand is left to re-arm and no status line has a re-arm note: every such routine's status line says "saves in a cloud run (v26)" (re-armed now, or earlier by anyone's `/setup-routines`), or this account's re-arm was declined (record the answer), or there are no routines. A stop or a "not now" leaves it unrecorded; a later run records it as soon as that holds, even with nothing left to ask.
