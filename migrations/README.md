# Migrations — how structural changes reach standing brains

A brand brain pins this factory at a release tag (`v1`, `v2`, …) via its `parker-system/` submodule. Moving the pin delivers new *method* automatically — but a change that reshapes the **brand repo itself** (a renamed path, a relocated file, a new standing surface, a new hook) doesn't arrive by pulling the mount. Migrations are how those changes travel.

## The contract

- **One file per release, every release:** `migrations/vN.md`, named exactly after the tag it belongs to. A release with no brand-side work still ships one — a one-liner no-op ("Nothing to do; the pin bump's re-sync delivers everything. Record `vN`.", see `v2.md`/`v3.md`) — so the record is complete and an updating brain never has to guess whether a missing file means "nothing to do" or "someone forgot."
- **Plain markdown, written for the agent running it.** A migration is a set of imperative, checkable instructions addressed to the Claude instance updating a brand brain: what to move, create, re-run, or edit *in the brand repo*, in what order, and how to verify it landed. Assume the brain being migrated was built at the previous release; state it explicitly when a step only applies to older layouts.
- **Idempotent and honest:** every step should be safe to re-run (check before acting: "if the file is already at the new path, skip") and must never touch brand data except in ways the instructions name. Steps that modify brand-authored content are shown to the team before applying, per `/update-brain`'s offer rules, unless the migration is marked `**Auto-apply:** yes` (below): then the edits are mechanical and the update reports them afterwards.
- **Applied in order by `/update-brain`:** when a brain takes a pin bump to `vB` (on its own, or on a yes), every `vN.md` after the ledger's **Migrations applied through**, up to B, runs in ascending order (normally that starts right after the old pin). The brain's `running-notes/standard-sync.md` records each migration as it finishes (`scripts/update-brain.py record-migration`, which refuses to skip one), so **Migrations applied through** is always the last one that completed, and **Pinned release** is the tag the mount is on (`record-pin`, which refuses a tag the mount isn't on).
- **A migration may stop partway.** When a step can't run yet (it waits for something outside the brain), the migration stops there, says why, and does not record its release. **Migrations applied through** stays at the previous release (a "not now" on one of its steps counts the same), and `/update-brain` finishes the missing migrations first on its next run, before any comparison; no newer release installs on its own until they're done. The pin bump, **Pinned release** and the sync script still go ahead; only **Migrations applied through** waits.
- **Migrations run first, the sync script runs once at the end.** On every pin bump, after the migrations finish, `/update-brain` runs `scripts/sync-executable-layer.py` to refresh the copied executable layer (the skills, agents, hooks, checker scripts, and schedule recipes the build copied out of the mount). A migration can rely on that order — it never needs to refresh those files itself.
- **A migration never touches what the script owns.** Never write a step that copies, refreshes, or diffs a file in the script's bundle map — the script does that deterministically, and a hand-rolled step will either duplicate it or fight it. Migrations do only what the script can't: layout moves and renames, new standing files outside the bundle, prompt re-runs, edits to brand-authored content. Before writing a step, check the bundle map in `scripts/sync-executable-layer.py`; if the path is in the map, delete the step. For a change that lives entirely inside the copied bundle, the migration is a one-liner no-op — "the pin bump's re-sync picks it up" (see `v2.md`/`v3.md`) is literal now.

- **Automatic updates (v40): say whether a migration can run with nobody there.** Standing brains on the standard layout install new releases on their own, through `/update-brain` and `scripts/update-brain.py plan`, but only as far as every migration on the way is safe to run unattended. A one-line no-op ("Nothing to do; ...", with no step headings or numbered steps) is safe as it is. A migration with real steps is safe only when it says so on its own line near the top: `**Auto-apply:** yes`. The test is whether a step needs a person, not whether it touches the brain's own files. Mark it `yes` when every step is mechanical and checks before acting, so a second run changes nothing:
  - copying a file in from the mount (a new seed, a folder README) where none exists, never over one that does;
  - adding a line to the update ledger or another running note, at a named place, when it isn't there yet;
  - adding a sentence to the brain's `CLAUDE.md`, or swapping an exact sentence for a new one, where the old text is found word for word, and skipping where it isn't (the team rewrote it);
  - a rename or move by a fixed list, skipping anything already moved or anything in the way;
  - a technical fix the team couldn't judge anyway (a settings line, a stale file the factory once wrote), when the step names the exact thing to change.

  An offer step (re-arm a routine, try something new) doesn't keep a migration from `yes` when every answer, "not now" included, finishes the step: with nobody there, `/update-brain` writes it to the ledger as a pending offer, the migration records, and the next session with someone there asks it. Leave the marker off, or write `**Auto-apply:** no`, when a step needs a decision only the team can make before it runs (which of two layouts, keep or drop something), regenerates or rewrites a doc's content, deletes or overwrites something the team wrote, merges a team-edited file by judgment, or needs something outside the brain (installing an app, changing an account). Such a migration needs a person: automatic updates stop at the release before it and offer the rest as one question, and it runs with the team there. When in doubt, leave the marker off. An automatic run doesn't show a marked migration's edits first; its closing summary names every file of the brain's own that a migration changed and what it added or swapped, and the brain's history keeps the old version. `tests/test_update_brain.py` checks every shipped migration classifies the way its text reads.
- **Seeds need a migration; bundle files don't.** A brand-owned starting file added to `SEEDS` in `scripts/scaffold-brain.py` reaches new brains only. If standing brains need it too, the migration creates it (check first, never overwrite). See `system/brain-scaffold.md`.
- **Scaffolded brains have nothing built to act on.** A brain with a `.scaffolded` file at its root was set up but never built. A step that re-runs a prompt, moves a built doc, or edits built content has nothing to do there: skip it and say so. Steps that touch the scaffold's own files (running notes, the brand lens, `parker_config.json`) still apply.

## The maintainer rule

Every release **ships its `migrations/vN.md` in the same PR that finishes it**, plus a `release-notes/` entry. A change that alters the brand-brain layout, renames or moves a path a brain references, adds a standing file outside the copied bundle, or edits brand-authored content writes real steps; a method-only or bundle-only change writes the one-liner no-op. `/update-parker-skill` carries this as a checklist item. Cutting a release (`git tag vN`) is manual and deliberate; the tag is what makes the accumulated changes — and their migration — visible to standing brains.
