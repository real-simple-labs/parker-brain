# v24 — cloud runs save the brain themselves

**Applies to:** brains on the standard layout (pinned `parker-system/` submodule, origin under `parker-brain/`). Self-managed brains (any other origin) sync their own way: skip both steps.

**What changes:** a cloud run (a scheduled cloud routine, or an agent in a hosted sandbox, with no Parker Desktop on the machine) can now save what it writes. It gets the brain through the Parker MCP tool `register_parker_brain_git_credential` and pulls, commits and pushes through Parker's git server itself. On a person's computer nothing changes: Parker Desktop syncs, and the agent runs no git. The re-sync delivers the rest: `save-brain` ("In a cloud run"), `git-guard.py` and `session-start.py` (both step aside or say so in a cloud run), `setup-routines` (the cloud-run preamble), the brand `AGENTS.md`, and the bundle READMEs. The maintainer contract is `parker-system/system/brain-sync.md`.

## Step 1 — add the cloud-run exception to the brain's `CLAUDE.md`

The root `CLAUDE.md` is the brain's own, so show the team the change before applying it.

The sentence below belongs in two places: at the end of the rule that starts **"Never run git here"** (just before "Full picture: `/save-brain`."), and at the end of the paragraph that starts "This folder is kept in sync by the **Parker Desktop app**". Check each place on its own: add the sentence where it is missing, and leave a place alone only when that place already has it. If the file words either one differently, add it after the sentence that says not to run git, in the same paragraph.

> **A cloud run is the one exception** (a scheduled routine or a hosted sandbox, with no Parker Desktop on the machine): nothing syncs it, so it gets the brain through the Parker MCP, pulls and commits, and pushes straight to `main` itself (`git push origin HEAD:main`; it has permission to, and never makes a branch), per `/save-brain`'s "In a cloud run".

Verify: `grep -c "In a cloud run" CLAUDE.md` prints 2, or 1 where the file has only one of the two places at all.

## Step 2 — re-arm cloud routines (only when the tool is there)

Routines armed before v24 start in the brain's GitHub storage, which a cloud routine often can't read, and nothing they write is saved.

**From v26 on, v26 does this step.** If this update moves `parker-system/` to v26 or later, skip this whole step (items 1 to 5 below) and record `v24` now: the routines v24's prompt armed stopped at their first step anyway, and `migrations/v26.md` re-arms them with the prompt that works. Remove any "needs re-arm (v24)" note from the status lines in `schedules/*.md` as you go; v26 writes its own.

1. Check the Parker MCP. If it has no `register_parker_brain_git_credential` tool, **stop this migration here**: tell the team that this last step waits for that tool, and do **not** record `v24`. The ledger then stays behind the pin, and the next `/update-brain` run finishes this migration first (step 1 finds its sentence in place and skips itself). Nothing else in the update waits for it: the pin and the re-synced files stay.
2. List this account's live schedules via `/schedule`, and read the status lines in `schedules/*.md`: they are the only view of routines armed from a teammate's account. If neither shows an active routine for this brand (live names carry its prefix, "[brand]: dream", …), skip the rest.
3. For this account's routines, offer to run `/setup-routines` again, and record the answer in the ledger like any other offer. A **"not now"** is a stop too: stop this migration here, say it will come back, and don't record `v24`, so the next `/update-brain` run offers it again. Only a yes (and the re-arm done) or a no finishes this step. It updates each routine in place: the cloud-run preamble in its prompt, the Parker MCP attached, a source repository that isn't the brain's, and a cloud environment that can reach `git.heyparker.ai` (full network access, or that host allowed).
4. A routine whose status line says another person armed it, and doesn't say "saves in a cloud run", was armed before v24 from that person's account, and only that account can re-arm it. Add "needs re-arm (v24): run `/setup-routines` from the account that armed it" to each such line that doesn't have it yet, and tell the team who needs to do it. The note goes when that person runs `/setup-routines` (it rewrites the line) or when the team says the routine is gone (mark it retired). While any status line still has the note, stop this migration here and don't record `v24`: the next `/update-brain` run checks again.
5. Routines the team made themselves (outside `/setup-routines`) aren't touched. If they asked for them, tell them that such a routine saves only when its prompt starts with the preamble in `.claude/skills/setup-routines/SKILL.md` step 2.

If this update moves `parker-system/` to v26 or later, record `v24` in `running-notes/standard-sync.md` once step 1 is done, and don't do step 2.

Otherwise, record `v24` only once step 2 is finished: this account's re-arm was taken or declined (record the answer), or it has no routines, and no status line still has the re-arm note. A stop or a "not now" leaves it unrecorded.
