# Process — Deliver to Slack

Put the finished statics where the team actually works. Optional, and only when the user asks or has standing instruction to.

## Before sending

**Sending to a channel is outward-facing.** Confirm the destination channel before posting unless the user already named it or has given standing authorization. A static posted to the wrong channel is not recallable in any meaningful sense.

Everything sent must have passed `judge-the-render.md`. Delivery is not a way around the judge.

## Execution

1. **Confirm the channel.** Name it back to the user before sending if they did not specify it.
2. **Send the asset with the context that makes it actionable.** A static with no note is a picture; the team needs to know what it is for.
3. **Keep the message short.** The gap it fills, the source of the copy, and anything blocking it. Three lines, not a report.
4. **Flag the dependencies visibly** — a missing shot or an unverified stat must be in the message, not in a thread reply. Someone will otherwise queue it for production as-is.
5. **Confirm what was sent** back to the user.

## What to include per static

- The asset, or the comp with `[COMP]` on it.
- The gap it fills, in one line.
- The copy source — the review or comment, quoted.
- Production dependencies and unverified stats, marked.

## What never to do

- Post to a channel the user did not confirm.
- Send an unjudged render.
- Send a comp without labeling it a comp.
- Bury a production dependency in a thread.
- Paste a wall of reasoning into a channel. The reasoning belongs in the conversation; the channel gets the asset and the decision.
