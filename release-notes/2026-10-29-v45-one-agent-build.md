# v45 — the build runs as one agent and reads the data once (2026-10-29)

A brain build ran each of its prompts in its own helper agent, and checked each output with another one. Every helper started empty, so it read the method again and pulled the brand's data again: one build made about a thousand Parker calls and read the same ads, reviews, comments, and competitor libraries many times over. The person pays for all of it out of their own Claude or Codex plan, and on a lighter plan the plan ran out long before the brain was built.

The first setup still builds every document and every audit. What changed is how.

## What shipped

- **One agent, no helper agents.** In `prompts/onboarding-runner.md`, "One agent, one prompt at a time" replaces the delegation contract: the build session runs every prompt itself, one at a time, branch by branch. The fidelity rule stays: every prompt is opened and read in full from its file before it runs, never from memory of a sibling or a summary. Each output is saved the moment it is done. After a compaction the build re-reads `BUILD-STATUS.md` and the next prompt's file; at a usage limit it stops cleanly, writes where it stopped, and resumes from there.
- **The data is pulled once.** New "Pull the data once" and Phase 0 step 8: the build pulls the brand's shared data into `build-data/`, with an `INDEX.md`: the brand's own ads (compact rows by window, breakdowns, the hook history, one file per ad for the ads the docs describe), the customer-language corpus (reviews, survey responses, ad comments), organic and TikTok, Reddit and forums, web pages, and each rival's library. Ad tools are asked for compact rows, with the heavy analysis only for the ads a doc describes. The folder carries its own `.gitignore` (`*`), so it never syncs; closeout deletes it.
- **A hook saves every pull; the model never types one.** Output tokens cost several times what input tokens cost, so a typed copy of a big pull costs more than pulling it again. The brain's PostToolUse hook (`pull-log.py`) now saves every Parker read into `build-data/pulls/` during a build, one record per line where the result is a list, and lists it in `build-data/pulls.md` with what the call asked for. It saves nothing without the folder's `.gitignore`, and never a setup, credential, status, or write tool. In Claude Code (its command now passes `--runtime claude`) a result over about 8,000 tokens reaches the model only as a short note: the file, its size, its fields, and its first records; the model reads the rest by slices. Codex gets the file too, its result in full, and an unchanged hook command, so nobody approves it again. Web pages are saved without their navigation and boilerplate, keeping every line a doc could quote or count.
- **Depth guards for one agent.** The first real one-agent build (on `<a brand>`, 2026-11-02) read about 3.3 MB in 103 Parker calls, against a median of 16.5 MB for helper-agent builds, and wrote about 40% of the words of the July helper-agent brain for the same brand, with competitor docs at about 11%. It also missed the account's retail-click metric (MikMak), the ad with the account's best hold rate, and a tracked rival. So the pull plan is wider: ads ranked by every conversion metric `list_custom_metrics` returns; creative reads for the lifetime top 10 by hook, hold, CTR, ROAS, and each conversion metric; full details for every profiled rival's top 10 by impressions and top 5 of the last 30 days; a full set and profile for every tracked rival that sells the same products to the same buyer; and web files that keep every quotable line. A doc reads its main source whole. "Follow the leads" tells the agent to chase what the data points at (an unused conversion metric, an ad that wins on something other than spend, a rival with no profile, a pointer to earlier work, two sources that disagree). And each doc family has an evidence floor in the self-check, which never blocks the build: a floor the data can't fill is written as data-limited and added to `missing-context.md`.
- **No thin persona or competitor docs.** The 11 competitor prompts, the competitive landscape, the single-competitor ad analysis, and the 12 persona prompts each get a short section right before their output: every section carries its own evidence (counts with denominator and window, verbatim lines with source and date, named ads with impressions rank and run dates, prices and pack names), a verdict comes only after the evidence that earns it and backs it on at least 2 surfaces or is labeled inferred or data-limited, the data goes in the doc as tables, and thin data is said exactly and marked data-limited instead of padded. In the same build, those docs ran at about 12% to 34% of the words of their helper-agent versions. The 7-day refresh in a paused build now also covers all-time lists that grow (reviews, comments), snapshots the team can edit (the brand persona, the custom metrics list), and saved chat threads, and `getMessages` pages until no more messages come back.
- **Every prompt reads from it.** The expertise block (synced into 73 prompts) and the team-conversations block (16) now say: during a build, read `build-data/` first (the doc's main source whole, the rest by slices), follow the leads, meet the evidence floor, pull only what it lacks (the hook saves it for the next prompt), and treat a pull from earlier in the build as the fresh pull. Only a slice whose window is still open (it ends today, or it is lifetime or a total to date) and that is more than 7 days old gets pulled again; a closed window stays. `voc-corpus-profile`, `brand-idea-bank`, and `gaps-opportunities-inspo` carry no expertise block and got the same rule in their source sections. Only the build's own steps read the folder: a refresh, a routine, or an on-demand run pulls live as before, even while a build is paused.
- **Compaction and old data, in code.** After a compaction mid-build, `session-start.py` tells the agent to open `BUILD-STATUS.md`, the next prompt, and the method docs again, and to read the data from `build-data/`. It also flags a `build-data/` folder left over from a finished build, or idle for more than 30 days, and has the agent offer to delete it: it holds raw customer text.
- **No check agent.** The per-prompt review and the build-completion review are passes the same agent runs itself, against the same checklists. A failed check gets one fix pass; a doc that still falls short is marked blocked and raised at the next phase boundary.
- **The rest follows the runner.** `/set-up-brain`, `prompts/README.md`, the factory `CLAUDE.md`, and `system/usage-logging.md` describe the new build. A one-agent build prints its `PARKER_USAGE` markers with a shell command, and `scripts/usage-log.py` now reads a marker from a tool result (Claude Code) or a command output (Codex), so the usage log still shows what each prompt cost. The empty marker `PARKER_USAGE {}` ends the label when the build pauses, stops, or closes.

## Migration

`migrations/v45.md`: nothing to do. The re-sync refreshes the hook files and the Claude `settings.json` where the team didn't edit them; an edited `settings.json` keeps the old pull-log command, so its pulls are saved but reach the model whole. A new build moves the pin to the newest release before it starts, so it gets this runner. A build already underway keeps the runner of its pin: automatic updates wait while a `BUILD-STATUS.md` sits at the root.
