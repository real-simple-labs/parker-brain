# v24 — cloud runs save the brain themselves (2026-09-28)

People set up scheduled routines in Claude's cloud (research something, refresh a doc, write a report into the brain), and nothing those routines wrote was ever saved. A cloud run has no Parker Desktop beside it, it could not push to Parker's storage, and a routine that used the brain's GitHub repository as its source often could not even read it. The customer saw the routine run and the brain stay the same.

Now a cloud run syncs the brain itself, through Parker's own git server. On a person's computer nothing changes: Parker Desktop syncs, and the agent runs no git.

## What shipped

- **What a cloud run is.** No `~/.parker/workspace.json` (no Parker Desktop on this machine) in a cloud environment: Claude Code cloud sessions and routines set `CLAUDE_CODE_REMOTE=true` (never set locally); any other cloud runner, such as a Codex cloud task, sets `PARKER_CLOUD_RUN=1`. A person's own computer is never one, with or without the app, because a person's own commits would lose who made each change.
- **`save-brain`: "In a cloud run".** Get access with the Parker MCP tool `register_parker_brain_git_credential` (the agent makes a secret in its shell and sends only its SHA-256; the secret never enters the conversation, the git config, or Parker's logs). Clone a fresh copy with the tool's `clone_command`, even when the run started in another copy (a filtered view's history differs from GitHub's). Pull before working; commit, pull and `git push origin HEAD:main` when done (every surface a cloud run reads grants the push to `main` in writing, because hosted sessions default to their own `claude/` branches); combine a clash by the keep-both rule; on `Authentication failed`, send the same hash again to renew. Without the tool, the run says plainly it could not save, as before.
- **`git-guard.py` steps aside in a cloud run.** Every git command passes there, pushes and merges included. On a person's computer every rule stands.
- **`session-start.py`** tells a cloud run to sync itself instead of saying the app does it.
- **`setup-routines`** registers each routine with a cloud-run preamble (get the brain through the tool, run the job in that copy, save to `main`), attaches the Parker MCP, gives the routine a source repository that isn't the brain's (the public factory), and asks for a cloud environment that can reach `git.heyparker.ai` (full network access, or that host allowed: the default "Trusted" network blocks it). The six schedule recipes' job lines say "this brand brain" instead of "the brand brain in this repo". When the Parker MCP has no such tool yet, it registers routines as before and says they can't save.
- **Docs.** `system/brain-sync.md` (the model, "Scheduled routines and other cloud runs", the guard), `system/schedules.md`, `system/codex-support.md`, the brand `CLAUDE.md` template, the bundled `AGENTS.md` and READMEs.
- **Tests.** `tests/test_runtime_hooks.py`: the guard lets a cloud run's clone, pull, commit, push, rebase and merge through under either signal, and blocks them with no signal, with `CLAUDE_CODE_REMOTE=false`, or with `workspace.json` present; the session-start hook gives the cloud line only in a cloud run. The helper strips both signals from the environment, so the suite gives the same verdicts inside a cloud session.

## For the other Parker repos

- **Backend (mevin):** `register_parker_brain_git_credential` (real-simple-labs/mevin#921, #928). It registers the hash for one person, one brain and one access mode for an hour, keyed so that a dev registration never works on the production git server, and decides access like `write_parker_brain` (the brand's team writes; an admin session outside Parker's own organizations reads). It runs outside production only for now. **Cut the `v24` tag after it is on in production**; before that, a brain's cloud routines can't use it, and `setup-routines` falls back to the old registration.
- **Web app, Parker Desktop:** nothing.

## Migration

`migrations/v24.md` has two steps: add the cloud-run exception to the brain's own `CLAUDE.md` (each of its two places checked on its own), and re-arm cloud routines with `/setup-routines`. A routine armed from a teammate's account gets a "needs re-arm (v24)" note in its `schedules/` status line, and only that teammate can re-arm it. If the Parker MCP doesn't have the tool yet, if the team says "not now", or while a re-arm note is left, the migration stops and leaves `v24` unrecorded. `/update-brain` changes so that a stopped migration really comes back: it walks migrations from the ledger's **Migrations applied through** (not from the old pin), records each one as it finishes, stops the walk at a migration that stops, writes only **Pinned release** at the end, and on its next run finishes whatever the ledger is behind on before comparing anything.
