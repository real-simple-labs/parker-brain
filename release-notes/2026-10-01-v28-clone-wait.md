# v28 — a cloud run waits for a long brain clone (2026-10-01)

A production routine on Parker AI (a 2.7 GB brain) got its key and started the clone, but the clone ran past the cloud shell's two-minute command timeout and the shell moved it to the background. The agent looked at the half-made copy, saw only `.git` and "No commits yet", took it for an empty brain, and reported that the brain didn't exist. The clone finished fine a minute later. Two other runs the same hour waited and saved, so nothing is wrong with the git server; the agent just needed to be told.

## What shipped

- **`scripts/cloud-run-git.py clone`** prints one line on stderr before the clone starts: a big brain takes several minutes, wait until the command prints the folder, and until then "No commits yet" means the clone is still running. The shell shows that line when it moves the command to the background. The line leaves the folder out, so the folder alone on stdout still means done.
- **`setup-routines`** (both copies): step 3 of the cloud-run preamble says to give the clone a long timeout (10 minutes) and wait until it prints the folder.
- **`save-brain`, "In a cloud run" step 2:** the same, plus: wait for the background notice, read "No commits yet" as a running clone only while the command runs, and judge the copy only after it has ended (a brain with no commits looks the same once its clone is done).
- **Tests.** `tests/test_cloud_run_git.py` checks that the wait line is out before git starts and holds no folder, and that both `setup-routines` copies carry the wait sentence.

The Parker MCP tool `register_parker_brain_git_credential` gives the same advice in its step 3 and right before the clone (mevin#946).
